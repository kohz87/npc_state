# NPC State v0.3 architecture

## Design rule

v0.3 preserves v0.2 user data, not v0.2 runtime machinery.

The runtime has four boundaries:

1. **Schema** owns durable dossier/state normalization.
2. **Scanner** converts chat evidence into one structured observation and applies it in code.
3. **Engine** serializes operations, validates chat/branch provenance, and commits atomically.
4. **Adapters/UI** connect the engine to SillyTavern without owning dossier truth.

## State domains

### Durable dossier

Identity, aliases, role/species/age, appearance, personality, behavioral profile, speech, mannerisms, background, memories, key relationships, player relationship state/history, archive/life state, portrait, manual locks, retention flags, and stale-lifecycle activity markers.

Stale lifecycle persists:

```text
lastActivityTurn
lastActivityMessageId
lastActivityReason
```

`lastActivityTurn` is a narrative assistant-turn index, not the number of scanner executions.

### Live scene state

`present`, `worldActive`, mood, location, goal, and status.

`present` means physical presence at the end of the latest successful scene observation. It is never used as a synonym for exchange participation.

### Ephemeral exchange observation

The latest committed observation stores:

```text
exchangeActiveNpcIds
finalPresentNpcIds
worldActiveNpcIds
targetNpcIds
```

`targetNpcIds` is exactly the union of exchange-active and final-present IDs.

## Scanner transaction

A normal assistant reply causes at most one current-cast structured generation. After JSON validation, the engine:

1. resolves stable NPC identities,
2. rejects tombstoned IDs and unsafe ID/name retargeting,
3. applies full patches only to the exact target set,
4. applies limited live-state patches to world-active-only NPCs,
5. applies relationship changes only to exchange-active targets using current-exchange evidence,
6. replaces strict physical presence from `finalPresentNpcIds`,
7. applies stale lifecycle activity/pruning to the same working state,
8. records one v0.3 branch checkpoint,
9. writes one sidecar revision.

Malformed JSON gets one bounded retry. A new user message invalidates the operation epoch; any late result is discarded before commit.

## Stale NPC lifecycle

Stale management is intentionally based on **narrative inactivity**, not simply being off-screen.

The default thresholds are:

```text
30 inactive assistant turns -> archive with archiveReason = "stale"
50 total inactive assistant turns -> remove stale archive
```

Both thresholds are configurable. The delete threshold is always greater than the archive threshold.

Activity is reset by the union of:

- current-exchange participation,
- final physical presence,
- explicit off-screen `worldActive`,
- an explicit canonical-name or alias reference in the current user + assistant exchange.

This retention-only reference check does not add an NPC to the full reconciliation target and does not create a new dossier from a mere mention.

Important safety rules:

- Re-scanning the same assistant message cannot advance stale age because the narrative turn index is unchanged.
- Existing/migrated dossiers with no stale activity marker establish a safe baseline on their first lifecycle-aware scan instead of being pruned from historical age.
- `retentionProtected` dossiers are never auto-pruned.
- Any dossier with manual stable-profile locks is also never auto-pruned.
- Manual and deceased archives are outside the stale auto-delete path.
- A stale archive that becomes narratively active again is restored automatically; restored final-present/world-active flags are preserved in that same transaction.
- Automatic stale deletion removes the stale dossier and structured social edges but deliberately does **not** add a manual deletion tombstone. This permits genuine later re-admission and branch recovery.
- Explicit user Delete still creates a tombstone and remains the stronger irreversible identity action.

The settings UI exposes a stale review surface with Open dossier, Reset activity, Protect, Archive/Restore, and explicit Delete controls.

## Portable bundle boundary

Bundle import/export is intentionally **not** raw sidecar copying. `bundle.js` defines a separate `npc_state_v3_bundle` format that carries the normalized v0.3 dossier schema and portable durable domains while excluding timeline/runtime machinery.

A full-chat bundle contains:

```text
format / formatVersion
appVersion / schemaVersion
bundleType = "full-chat"
source.chatKey
source.narrativeTurn
source.exportedAt

data.npcs
data.socialGraph
data.suppressedNames
data.deletedNpcIds
```

A selected-NPC bundle uses `bundleType = "npc"`, contains exactly one normalized dossier, and includes social edges touching that stable NPC ID. The counterpart dossier is not duplicated into the bundle; such an edge is retained on import only when the counterpart stable ID already exists in the destination or is imported by the same bundle.

The bundle deliberately excludes:

- `revision`,
- `lastScannedMessageId`,
- `lastObservation`,
- branch checkpoints,
- branch baseline snapshots,
- branch head lineage,
- branch-safety/runtime state,
- migration provenance,
- per-process operation locks/epochs and other engine memory.

### Validation and normalization

Before preview or commit, imports require:

- exact `npc_state_v3_bundle` format,
- supported bundle format version,
- current v0.3 schema version,
- a v0.3 app-version family,
- stable IDs and canonical names on every dossier,
- no duplicate stable IDs or duplicate canonical identities inside the bundle,
- no bundle that marks the same stable ID as both a live dossier and a deletion tombstone.

Every incoming dossier is then passed through `normalizeNpc`, and graph/tombstone/name collections pass through the normal v0.3 state normalizer. Unknown legacy/runtime dossier fields therefore disappear at the import boundary rather than leaking into persistence.

### Merge conflict model

Safe merge has two independent policies:

1. **Matching stable ID**: keep the current dossier or replace its portable dossier data with the imported version.
2. **Hard identity conflict**: abort the whole import or skip the conflicting imported identity.

Hard conflicts include:

- the same stable ID naming a different canonical identity,
- the same canonical name already belonging to another stable ID,
- an incoming live dossier whose stable ID is locally tombstoned,
- an imported tombstone targeting a live local dossier.

The default is conservative: keep current matching dossiers and abort on any hard conflict.

Local manual-deletion tombstones are authoritative during merge and cannot be silently resurrected. Imported tombstones likewise cannot silently delete a live local dossier. When conflict policy is `skip`, only imported conflicting identities/edges are ignored; existing local dossiers and social edges are left untouched.

### Full-chat replace

`replace` is available only for a full-chat bundle and is the explicit restore operation. It replaces the portable durable domains:

```text
npcs
socialGraph
suppressedNames
deletedNpcIds
```

Destination branch checkpoints/baseline/lineage remain local because they belong to the current SillyTavern chat timeline, not the imported bundle. Live `present`/`worldActive` flags are cleared on imported dossiers, `lastObservation` is cleared, and `lastScannedMessageId` is reset so source-chat presence is never injected as if it were current truth.

### Cross-chat rebasing

When source and destination chat keys differ:

- dossier message IDs are cleared,
- relationship-history `sourceMessageId` values are cleared,
- social-edge `sourceMessageId` values are cleared,
- live presence/world activity is not imported,
- stale activity is rebased by preserving **relative inactivity age**:

```text
source inactive age = sourceNarrativeTurn - source lastActivityTurn
new lastActivityTurn = destinationNarrativeTurn - source inactive age
```

This preserves stale-age meaning without pretending source message indexes exist in the destination chat.

### Commit semantics

Export and preview are read-only. Import re-validates against the current state inside the per-chat serialized engine operation. A successful import receives one destination branch checkpoint (`bundle-merge` or `bundle-restore`) and one sidecar write. A rejected conflict performs no partial state mutation or sidecar write.

## Portrait prompt boundary

Portrait prompt support is deliberately a **settings/UI helper**, not part of the dossier engine or image-generation pipeline.

The v0.3 settings object stores only:

```text
portraitPromptMode            natural | tags | hybrid
portraitPreset.positive       free-form positive preset text
portraitPreset.negative       free-form negative preset text
portraitPositivePrompt        free-form positive template
portraitNegativePrompt        free-form negative template
```

`portrait-prompt.js` resolves both templates locally from one normalized dossier. The defaults are:

```text
positive: {{positivePreset}}\n{{character}}
negative: {{negativePreset}}
```

`{{character}}` is the only mode-sensitive placeholder:

- `natural` builds readable portrait prose from known dossier fields,
- `tags` builds comma-separated prompt fragments,
- `hybrid` combines compact identity tags with natural appearance/bearing text.

Direct dossier placeholders such as `{{name}}`, `{{species}}`, `{{appearance}}`, `{{personality}}`, `{{mood}}`, and `{{status}}` are also available and are not rewritten according to mode. Unknown placeholders remain visible so template mistakes are not silently hidden. Missing dossier facts resolve empty and no visual facts are inferred. The first-pass `{{portraitPreset}}` placeholder remains accepted as a positive-preset alias for compatibility.

`portrait-ui.js` owns only settings editing, explicit Save, selected-NPC positive/negative preview, and clipboard copy for either channel or both together. Unsaved draft text is kept in the mounted form during ordinary state refreshes. Saved prompt settings live in extension settings rather than per-chat sidecars or portable bundles.

This subsystem contains no:

- image provider/API call,
- model call,
- automatic portrait generation,
- regeneration workflow,
- generation queue,
- polling/retry state,
- portrait job records.

Existing `npc.portrait` data remains a durable dossier field for migrated/imported images, but prompt composition does not mutate it.

## Canonical dossier UI boundary

The Dossier Library remains one canonical viewer. The redesign changes presentation only; it does not add a second state surface or duplicate dossier logic.

`ui.js` owns selection, actions, editor opening, refresh wiring, archive/restore/delete wiring, and entry from settings/stale/present-card surfaces. `dossier-view.js` is a pure presentation helper that owns:

- portrait-first dossier markup,
- cast-card markup,
- lifecycle labels/classes,
- deterministic cast sorting,
- search filtering.

The library shell has three visual regions:

```text
header
selected dossier
bottom cast rail
```

Desktop and landscape tablet render the selected dossier as a split view with a dominant portrait hero on the left and an independently scrolling document on the right. Portrait tablet and phone layouts stack the portrait hero above one vertical document column. The cast rail remains outside the dossier document scroll in every layout so character switching does not require reaching the end of a long dossier.

The bottom cast rail is a navigation projection of the same `state.npcs` collection. It does not own a second cast list or persistence layer. Its default order is:

```text
present
worldActive
ordinary active/off-screen
archived
```

then canonical-name order within each group. Search matches name, aliases, role, species, and lifecycle label. Selecting a card changes only `selectedNpcId` and rerenders the same canonical detail surface.

Important UI invariants:

- Present cards, stale review, settings roster, and direct API opens all converge on `openLibrary(reference)`.
- An explicit external open clears an existing cast search so the requested stable ID cannot remain hidden by a stale filter.
- The selected cast card is centered after an explicit switch.
- A background refresh of the same selected dossier preserves the document scroll position.
- The portrait rail is responsive and touch-scrollable; it does not replace strict presence semantics with visual proximity.
- UI sorting and search never mutate the durable NPC array.
- No model call, storage write, relationship update, stale reset, or presence change occurs merely from opening or navigating the library.

Dossier text is presented in distinct Current, Relationship, Personality, Appearance, Behavioral profile, Speech, Mannerisms, Key relationships, Important memories, Background, and relationship-history blocks. These are views over existing normalized fields, not new schema domains.

## Targeted dossier refresh

A targeted refresh can recover stable dossier facts and memories from recent chat but:

- does not replay relationship deltas,
- does not change global physical presence,
- does not replace the latest exchange observation,
- never reads or saves editor DOM state,
- receives its own branch checkpoint.

A targeted refresh is a dossier maintenance action rather than story progression, so it does not advance narrative stale age by itself.

## Editor safety

The editor is bound to one stable NPC ID. Saving requires both:

- the editor shell ID to equal the active editor ID, and
- the dossier `updatedAt` value to equal the version captured when the editor opened.

This prevents both cross-NPC corruption and stale same-NPC overwrites.

## Persistence

v0.3 uses `npc_state_v3_chat_data` sidecars and deterministic `npc-state-v3-*.json` filenames. Writes are guarded by:

- per-chat in-process serialization,
- `navigator.locks` when available,
- a localStorage lease fallback,
- revision comparison against the remote sidecar,
- a local pointer hint that detects a first-write race across tabs.

A configured pointer whose file is missing is an error. v0.3 will not silently create a blank replacement over unknown durable state.

## v0.2 importer

The only compatibility boundary is `migrate-v02.js`. It reads the old `npc_state_chat_data` sidecar, normalizes durable fields into the v0.3 whitelist schema, writes a new v0.3 sidecar, and leaves the old file untouched.

Legacy operation queues, locks, and branch checkpoints do not cross this boundary.

Legacy/imported dossiers without v0.3 stale activity markers begin from a safe baseline on their first lifecycle-aware scan. This avoids immediately archiving or deleting old dossiers merely because the feature did not exist when their prior activity occurred.

## Branch model

The first v0.3 load records a baseline snapshot/lineage. Later v0.3 writes record bounded checkpoints.

When the current chat lineage changes:

- if the stored branch head is still a prefix, no rollback is needed;
- otherwise the engine restores the deepest matching v0.3 checkpoint/baseline;
- deletion tombstones are unioned into the restored state, preventing resurrection of explicit manual deletions;
- automatic stale cleanup is branch-recoverable because it does not create a tombstone;
- if the current branch diverges before the first v0.3 baseline, the engine marks the branch `prebaseline-diverged`, clears live presence, and pauses scanning/injection.

That last case is deliberately fail-closed because v0.2 branch checkpoints are not imported.

## Deliberately removed concepts

v0.3 does not contain:

- automatic cast-wide backfill queues,
- `deepSweep`/`silent` queue flags,
- runtime monkey-patching of `getContext().generateRaw`,
- dossier-fingerprint participant inference,
- a duplicate off-screen dossier renderer,
- detached per-NPC full-cast refresh loops,
- automatic portrait-generation queues or provider plumbing.
