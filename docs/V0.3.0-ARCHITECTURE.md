# NPC State v0.3 architecture

## Design rule

v0.3 preserves v0.2 user data, not v0.2 runtime machinery.

The runtime has four boundaries:

1. **Schema** owns durable dossier/state normalization.
2. **Scanner** converts chat evidence into one structured observation and applies it in code.
3. **Engine** serializes operations, validates chat/branch provenance, and commits atomically.
4. **Adapters/UI** connect the engine to SillyTavern without owning dossier truth.

## State domains

### Durable dossier

Identity, aliases, role/species/age, appearance, personality, behavioral profile, speech, mannerisms, background, memories, key relationships, player relationship state/history, archive/life state, portrait, manual locks, and retention flags.

### Live scene state

`present`, `worldActive`, mood, location, goal, and status.

`present` means physical presence at the end of the latest successful scene observation. It is never used as a synonym for exchange participation.

### Ephemeral exchange observation

The latest committed observation stores:

```text
exchangeActiveNpcIds
finalPresentNpcIds
worldActiveNpcIds
targetNpcIds
```

`targetNpcIds` is exactly the union of exchange-active and final-present IDs.

## Scanner transaction

A normal assistant reply causes at most one current-cast structured generation. After JSON validation, the engine:

1. resolves stable NPC identities,
2. rejects tombstoned IDs and unsafe ID/name retargeting,
3. applies full patches only to the exact target set,
4. applies limited live-state patches to world-active-only NPCs,
5. applies relationship changes only to exchange-active targets using current-exchange evidence,
6. replaces strict physical presence from `finalPresentNpcIds`,
7. records one v0.3 branch checkpoint,
8. writes one sidecar revision.

Malformed JSON gets one bounded retry. A new user message invalidates the operation epoch; any late result is discarded before commit.

## Targeted dossier refresh

A targeted refresh can recover stable dossier facts and memories from recent chat but:

- does not replay relationship deltas,
- does not change global physical presence,
- does not replace the latest exchange observation,
- never reads or saves editor DOM state,
- receives its own branch checkpoint.

## Editor safety

The editor is bound to one stable NPC ID. Saving requires both:

- the editor shell ID to equal the active editor ID, and
- the dossier `updatedAt` value to equal the version captured when the editor opened.

This prevents both cross-NPC corruption and stale same-NPC overwrites.

## Persistence

v0.3 uses `npc_state_v3_chat_data` sidecars and deterministic `npc-state-v3-*.json` filenames. Writes are guarded by:

- per-chat in-process serialization,
- `navigator.locks` when available,
- a localStorage lease fallback,
- revision comparison against the remote sidecar,
- a local pointer hint that detects a first-write race across tabs.

A configured pointer whose file is missing is an error. v0.3 will not silently create a blank replacement over unknown durable state.

## v0.2 importer

The only compatibility boundary is `migrate-v02.js`. It reads the old `npc_state_chat_data` sidecar, normalizes durable fields into the v0.3 whitelist schema, writes a new v0.3 sidecar, and leaves the old file untouched.

Legacy operation queues, locks, and branch checkpoints do not cross this boundary.

## Branch model

The first v0.3 load records a baseline snapshot/lineage. Later v0.3 writes record bounded checkpoints.

When the current chat lineage changes:

- if the stored branch head is still a prefix, no rollback is needed;
- otherwise the engine restores the deepest matching v0.3 checkpoint/baseline;
- deletion tombstones are unioned into the restored state, preventing resurrection;
- if the current branch diverges before the first v0.3 baseline, the engine marks the branch `prebaseline-diverged`, clears live presence, and pauses scanning/injection.

That last case is deliberately fail-closed because v0.2 branch checkpoints are not imported.

## Deliberately removed concepts

v0.3 does not contain:

- automatic cast-wide backfill queues,
- `deepSweep`/`silent` queue flags,
- runtime monkey-patching of `getContext().generateRaw`,
- dossier-fingerprint participant inference,
- a duplicate off-screen dossier renderer,
- detached per-NPC full-cast refresh loops.
